# LightGBM이 뭐고, exp_001에서 왜 썼나 (회의 설명용)

`experiments/exp_001_lightgbm_derived_features.md`의 기술적 기록을
이해하기 쉽게 풀어쓴 문서입니다. 회의 때 이 순서대로 말하면 됩니다.

---

## 1. 한 줄 요약

**LightGBM은 "여러 개의 작은 결정 나무(decision tree)를 순서대로 이어
붙여서, 앞 나무가 틀린 부분을 다음 나무가 보완하도록" 학습하는 모델
이에요.** 베이스라인이 쓴 RandomForest도 "나무를 여러 개 쓴다"는 점은
같지만, 나무를 쌓는 **방식**이 근본적으로 다릅니다. 이 차이 때문에
LightGBM이 이런 종류의 정형(표 형태) 데이터에서 보통 더 좋은 성능을
냅니다.

## 2. RandomForest vs LightGBM — 나무를 쌓는 방식의 차이

둘 다 "결정 나무(decision tree)"를 여러 개 만들어서 합치는 **앙상블
모델**이라는 공통점이 있어요. 차이는 나무들이 서로 어떤 관계인가입니다.

**RandomForest = 배깅(bagging) — 나무들이 서로를 모른다**
- 나무 100개를 각자 랜덤한 데이터 일부만 보고 **독립적으로, 동시에** 만듦
- 최종 예측은 100개 나무의 결과를 평균
- 비유: 서로 다른 100명이 각자 따로 문제를 풀고, 마지막에 다수결/평균을 냄
- 장점: 안정적이고 과적합(overfitting)에 강함
- 우리 베이스라인은 이 나무들을 일부러 얕게(`max_depth=10`) 그리고
  보수적으로(`min_samples_leaf=200`, 한 잎에 최소 200개 표본 필요)
  설정해뒀어요 — 그래서 미세한 신호를 잘 못 잡아내는 경향이 있습니다.

**LightGBM = 부스팅(boosting) — 나무들이 서로의 오답노트를 본다**
- 나무 1을 만들고 예측 → 어디서 많이 틀렸는지 계산
- 나무 2는 **나무 1이 틀린 부분을 집중적으로 맞히도록** 학습
- 나무 3은 나무 1+2가 합쳐도 여전히 틀린 부분을 다시 보완
- 이걸 수백 번 반복 (exp_001에서는 173번째에서 자동으로 멈춤 — 아래 6번 참고)
- 비유: 한 사람이 문제를 풀고, 틀린 문제만 모아서 오답노트를 만들고,
  그 오답노트로 다시 공부하고, 또 그중 틀린 것만 추려서... 를 반복
- 장점: 데이터의 미세한 패턴까지 잡아내서 정확도가 보통 더 높음
- 단점: 오답노트에 너무 집착하면 "이 문제집에만 통하는 요령"을 외워버릴
  위험(과적합)이 있음 → 그래서 검증 데이터로 계속 감시하면서 적당한
  시점에 멈추는 장치(early stopping)가 필수

## 3. 이름의 "Light"는 왜 붙었나 — 왜 빠른가

LightGBM은 Microsoft가 만든 구현체로, 같은 부스팅 계열인 XGBoost보다
**속도와 메모리**에 최적화된 게 특징이에요. 실제로 이번에 학습 시간이
RandomForest 76초 → LightGBM 9.6초로 8배 가까이 빨랐습니다. 이유:

- **나무를 키우는 방향이 다름**: 보통의 나무는 "층(depth)"을 한 층씩
  고르게 넓혀가며 자라는데, LightGBM은 "지금 가장 손해(오차)가 큰
  가지"부터 우선적으로 찢어나감(leaf-wise). 같은 개수의 가지를 써도
  오차를 더 빨리 줄임
- **연속된 숫자를 구간(bin)으로 묶어서 분할 지점을 탐색**: 모든 값을
  하나하나 비교하지 않고 히스토그램처럼 구간화해서 훨씬 빠르게 "어디서
  나눌지" 결정
- **범주형 컬럼(`top_bottom`, `game_type`, `base_state`)과 결측치를
  자체적으로 처리**할 수 있어서 전처리 부담이 적음 (이번엔 Windows
  환경 버그 때문에 범주형은 결국 베이스라인처럼 정수 인코딩으로
  우회했지만 — 6번 참고)

## 4. 이 대회에서 LightGBM을 고른 이유 (구체적으로)

1. **데이터가 표 형태(tabular)이고 숫자형+범주형이 섞여 있음** — 이런
   데이터에서는 딥러닝보다 트리 기반 모델(RandomForest, LightGBM,
   XGBoost 등)이 여전히 정석적인 선택이에요. 그중에서도 부스팅 계열이
   보통 배깅 계열보다 성능이 좋습니다.
2. **베이스라인이 일부러 약하게 설정된 RandomForest**였어서, 같은
   트리 기반이지만 미세 신호를 더 잘 잡는 부스팅으로 바꾸면 개선
   여지가 크다고 판단했어요.
3. **학습이 빨라서 반복 실험에 유리** — 오늘처럼 시간이 촉박한
   상황에서 한 번 돌리는 데 10초 안팎이면, 이것저것 바꿔보며 여러 번
   시도할 수 있어요.
4. **업계/대회에서 정형 데이터 표준으로 널리 쓰임** — 문제가 생겨도
   참고할 자료나 팀원들의 사전 지식이 많은 편이라 협업하기 좋아요.

## 5. exp_001에서 실제로 한 일 (회의에서 말할 스크립트)

> "베이스라인 RandomForest는 트리를 얕고 보수적으로 설정해서 신호를
> 충분히 못 잡는다고 판단했어요. 그래서 같은 트리 기반이지만 이전
> 나무의 오차를 다음 나무가 보완해나가는 방식인 LightGBM(그래디언트
> 부스팅)으로 바꿔봤습니다. 동시에, 기존 47개 공식 피처에 카운트
> 상황·접전 여부·투수 최근 폼 변화·구종 다양성 같은 파생 피처 15개를
> 추가했어요 — 전부 해당 투구 시점에 이미 알 수 있는 정보로만 계산해서
> 리키지(규칙 위반) 위험은 없습니다.
>
> 결과적으로 로컬 검증 점수가 415.57에서 628.51로 약 51% 개선됐어요.
> 다만 이번엔 시간이 없어서 '피처 추가 효과'와 '모델 교체 효과'를
> 한 번에 같이 바꿔버렸기 때문에, 정확히 뭐가 얼마나 기여했는지는
> 아직 몰라요 — 이걸 다음 실험에서 나눠서 확인하는 게 우선순위라고
> 생각합니다."

## 6. 질문 대비 — 주의할 점 / 한계

- **과적합 방지**: 부스팅은 오답노트를 계속 파다 보면 검증 데이터에만
  맞춰버릴 위험이 있어서, `early_stopping`을 걸어 검증 점수가 100번
  연속 개선 안 되면 멈추도록 했어요. 실제로 173번째 나무에서 멈췄고,
  최종 제출용 모델은 전체 데이터로 그 횟수(173)만큼만 다시 학습했습니다.
- **피처/모델 효과 미분리**: 위에서 언급한 대로, 다음 실험에서 반드시
  분리해서 검증할 예정.
- **실제 개발 중 발견한 버그**: LightGBM 모델을 파이썬의 일반적인
  저장 방식(joblib/pickle)으로 저장했다가 다른 프로세스에서 불러오면
  이 환경에서 크래시가 나는 문제를 발견해서, LightGBM 자체 저장
  포맷으로 바꿔 해결했어요. 팀원 중 누군가 LightGBM을 쓸 때 같은
  문제를 겪을 수 있으니 미리 공유하면 좋을 내용이에요.
